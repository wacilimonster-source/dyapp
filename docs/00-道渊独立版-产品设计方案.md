# 《道渊》独立版 · 产品设计方案

> 版本：v0.1（方案稿）　日期：2026-10-12
> 目标：把酒馆（SillyTavern）角色卡《道渊》v5.3 重做成一个 **AI 驱动的修仙独立游戏 APP**
> 定位一句话：**引擎管账本与规则，模型管演出与自由剧情。**

---

## 0. 电梯陈述

《道渊》现在其实是「一张塞满世界观与变量的提示词卡」：20 万字世界书、18 万字创角界面、20 万字状态栏模板、319 条设定条目、MVU+Zod 变量系统、动态遭遇、三重人格合理性审查——**它已经是一个小游戏引擎，只是被迫运行在聊天框里，靠正则替换当渲染层、靠模型自觉当状态机。**

独立版要做的事，是把这套已经存在的「引擎」从提示词里**搬出来、落地成真正的程序**：

- 把**状态与规则**从 prompt 里搬进本地引擎（确定性、可校验、不掉档）；
- 把**世界书检索**从"常驻注入 + 手动开关"换成"按需检索注入"（省 token、准命中）；
- 把**界面**从"模型吐 HTML + 正则替换"换成原生渲染（真正的状态栏、角色卡、地图、图鉴、演出）；
- 把**AI 对话**保留为内核——世界推进、对白、情感、自由剧情仍由 LLM 驱动。
- 外面套一层**独立游戏的壳**：主菜单、创角、存档、图鉴、成就、镜头演出。

## 1. 背景

### 1.1 《道渊》是什么（卡片实测盘点）

| 维度 | 实测结果 |
|---|---|
| 题材 | 修仙开放世界沙盒文字冒险，成人向（NSFW），玄天界 / 仙界双界 |
| 世界书 | **319 条**，正文合计约 **20.4 万字**（势力 / 人物 / 地点 / 秘境 / 境界 / 规则 / 数值） |
| 卡片字段 | `description` 短（系统指令，约 300 字）；`first_mes` 为欢迎页 HTML；`alternate_greetings` 仅 1 条且只有 6 字 `[重塑仙缘]` 作为占位标记 |
| 正则脚本 | **17 条**：状态栏美化、变量去除、创角界面（18.5 万字）、NPC 注入（玄天界/仙界 × 低阶/高阶）、绝色榜注入 |
| 脚本宿主 | **4 个**：`MVU`（变量引擎）、`ZOD`（状态 Schema，8.2 千字）、`道渊配置助手`、`道渊Wiki`（均外链 CDN 脚本） |
| 变量模型 | MVU 消息级变量 + Zod Schema：`世界 / 主角 / 道侣 / 灵宠 / 人物 / 机遇 / 绝色榜 / 玉简` 八大块 |
| 开局流程 | 欢迎页 → 点击「开始仙途」→ 切到 swipe 1 → `[重塑仙缘]` 被正则替换成 18.5 万字创角界面 → 生成系统消息 `... | /cut | /trigger` |
| 每回合协议 | 模型在正文末尾输出 `<UpdateVariable>` + JSON Patch（replace/delta/insert/remove）维护变量 |
| 隐性机制 | 动态遭遇（`遭遇冷却` 归零时按境界/场景抽 `[RANDOM_NPC]`）、DC 点数判定体系、道心值四境、合理性审查三重人格（审理 30 条铁律 / 衡平 / 天道） |

> 详见 `附录A·道渊卡片资产盘点.md`、`附录B·状态数据模型.md`，原始提取见 `_卡资产提取/`。

### 1.2 卡片的痛点（为什么值得独立化）

1. **提示词负担极重**：单卡内含 ~20 万字世界书 + 18.5 万字创角脚本 + 20 万字状态栏模板。这些内容以文本形态挤进上下文与正则替换，模型每回合都被海量设定和格式要求淹没，真正用于"演好这一段戏"的注意力被稀释。
2. **变量系统脆弱**：状态靠 MVU + Zod + **模型手写 JSON Patch** 维护。路径写错、漏写、格式漂移都会导致"掉档"；一致性完全押在模型自觉上，长对话必然衰减。
3. **可视化被卡住**：所有"界面"都是模型吐 HTML、正则替换后塞进消息气泡。样式受酒馆容器限制，**无法做真正的游戏化交互**——不能点击、不能拖拽、没有动画、没有二级页面、没有面板切换。
4. **没有游戏壳**：没有主菜单、存档管理、图鉴、成就、镜头演出，本质仍是聊天窗。
5. **检索粗放**：319 条世界书主要靠 `constant` 常驻 + EJS 手动开关（`getwi()`）注入。**要么全塞（浪费 token），要么手动开关（易漏）**，缺乏按当前场景的智能命中。
6. **上手摩擦大**：要靠用户自己装酒馆助手、配提示词模板、理解悬浮配置助手、处理出生地切换；换设备/换酒馆环境就重来。

### 1.3 目标 / 非目标

**目标**
- 把卡内机制 100% 复刻并**升级为本地确定性系统**，不改变世界观与内容；
- 每回合**有效上下文显著下降**、状态**零掉档**；
- 提供真正的**游戏化可视化**（原生状态栏 / 面板 / 地图 / 图鉴 / 演出）；
- 单机可玩、可存档、可导入导出，跨平台（桌面优先，移动可用）。

**非目标（本期不做）**
- 不做多人/联网社交、排行榜；
- 不做图形化战斗（保持文字叙事，仅做"判定演出"）；
- 不改编/重写原作设定（尊重原作，做"引擎 + 界面"，不做"另起炉灶"）；
- 不做商用分发（见第 8 节合规）。

## 2. 产品定位

### 2.1 核心体验：AI 沙盒叙事 × 游戏化外壳

| 层 | 负责谁 | 例子 |
|---|---|---|
| **叙事层**（灵魂） | **LLM** | 剧情推进、对白、NPC 反应、机遇内容、世界细节、情感演出 |
| **规则层**（骨架） | **本地引擎** | 数值 clamp、境界突破、修炼产出、DC 查表、抽取气运、遭遇触发、时间推进 |
| **界面层**（皮相） | **APP 原生** | 状态栏、角色卡、关系图、地图、背包、玉简、Wiki、演出动画 |

一句话：**模型演"发生什么"，引擎算"于是怎样"，界面演"给你看"。**

卡的原设计是"模型既演戏又记账又画 UI"，三者相互污染。独立版把它们解耦——这也正是"优化调用"和"可视化"两个诉求的同一把钥匙。

### 2.2 目标用户与场景

- **主用户**：现有《道渊》玩家（已熟悉修仙沙盒与成人向内容），希望"更好用、更好看、更不崩"。
- **场景**：桌面端长时沉浸（1–3 小时一次游历）；移动端碎片化推进剧情。
- **前提**：用户自带 LLM API（OpenAI 兼容 / 本地 Ollama / 中转），APP 不内建付费模型。

### 2.3 五条设计原则

1. **状态出提示词（State-out-of-Prompt）**：权威状态存在本地，模型只读得到"当前摘要"，只写"意图"。
2. **按需检索（Retrieval-over-Dump）**：319 条设定按场景检索注入，不再全量常驻。
3. **确定性优先（Deterministic-first）**：能本地算的绝不交给模型（掷骰、查表、clamp、时间、抽取）。
4. **原生渲染（Native Render）**：模型永不输出 HTML/状态栏；界面全部 APP 画。
5. **叙事不设限（Narrative Freedom）**：除规则与一致性外，剧情完全自由，保留卡的沙盒灵魂。

## 3. 玩法与系统设计

### 3.1 游戏主循环

```
创角 → [主界面] ⇄ 玩家行动
                 ↓
        引擎组装本回合上下文（检索 + 状态摘要 + 近况）
                 ↓
        LLM 生成叙事 + 结构化"效果意图"
                 ↓
        引擎校验并落地效果（clamp / 查表 / 掷骰 / 写库）
                 ↓
        界面更新（叙事流 + 状态栏 + 数值动效 + 事件卡）
                 ↓
        （遭遇冷却归零 → 引擎触发动态遭遇）
```

每回合产出一份 **TurnResult**：`narrative`（叙事文本）+ `effects[]`（语义效果）+ `scene`（场景/时间/地点/危机）+ 可选 `choices[]`（引擎推荐的行动建议）。

> **关键改进**：把卡的"模型手写 JSON Patch"换成"模型输出语义效果 + 引擎落地"。模型写 `{type:"damage", target:"主角", amount:12, reason:"被毒针擦伤"}`，引擎负责 clamp 到 0–100、写入、并回显动画。**模型不需要记住中文变量路径，也就不会写错路径。**

### 3.2 创角（重做「重塑仙缘」）

把 18.5 万字的单页 HTML 向导，重做成 APP 内**分步、可保存草稿、带演出**的创角流程：

1. **身份**：姓名 / 性别 / 出身背景（影响初始道心与宗门）
2. **灵根抽取**：转动抽取动画，品阶（天/地/玄/黄/凡）按卡内概率表
3. **气运自选/抽取**：默认「自选模式」（卡 v5.3 已改为直接进自选）；气运池分类（女性向/男性向/通用），支持作弊开关、真·气运 5% 概率
4. **功法/器物/储物袋**：初始配置
5. **天定道侣**：可选，可自定义
6. **出生界**：玄天界（默认）/ 仙界
7. **确认**：生成 `初始状态快照`（对应卡的 `[initvar] 初始` 世界书）+ 开局叙事

创角产物直接写成本地存档的初始 `GameState`，**同时**渲染成一段"开局信息"文本喂给模型做第 0 回合（对应卡里"首次回复初始化"的规则，但由引擎保证不遗漏）。

### 3.3 数值与境界

复刻卡内五大核心资源 + 道心，本地强类型 + clamp：

| 资源 | 含义 | 归零后果 | 恢复 |
|---|---|---|---|
| 生命 | 肉身生命力 | 死亡 | 疗伤/静养/丹药/高阶法则重塑 |
| 精血 | 生命本源（关联寿元） | 本源枯竭 | 天材地宝，极难恢复 |
| 灵力 | 施法能量 | 无法动用术法 | 打坐/灵石/丹药 |
| 修为 | 境界积累 | 不满不突破 | 修炼/丹药/顿悟/传承 |
| 神识 | 神魂意志 | 神魂溃散 | 静养/神魂丹药 |
| 道心 | 道途坚定度（0–100，四境） | 走火入魔 | 感悟/坚守/羁绊 |

- **模糊感知**：UI 默认显示"充盈/稳固/虚弱…"的模糊语（贴合卡设定"主角无法感知具体数值"），可在设置里开"神视模式"看精确数字。
- **境界体系**：炼气→筑基→金丹→元婴→化神→炼虚→合体→大乘→渡劫→真仙→金仙→玄仙→仙帝→半步超脱→超脱，**每境界 DC 由引擎查表**（凡 0 … 超脱 999）。
- **突破**：小境界修为满 100 自动圆满；大境界需对应丹药；炼虚起需悟法则 + 渡劫。**掷骰交给引擎**（按道心/灵根/丹药加成算成功率），结果告诉模型去演"成/败"。
- **修炼**：单次基础 30 日，境界越高翻倍；产出按灵根品阶表（炼气 +10~30 / 高阶 +3~10）。全部本地结算。

### 3.4 气运 / 灵根 / 功法 / 器物 / 背包

- **气运**：`类型 / 效果 / 使用状态 / 压制状态`，UI 用 chip 展示，可点开详情。真·气运高亮标记。
- **灵根**：品阶 + 描述，影响修炼表，UI 做专属徽记。
- **功法/器物**：熟练度进度条、损耗度、状态；器物可做"耐久"可视化。
- **背包（储物袋）**：数量归零自动清理（对应卡内 `_.pickBy(数量>0)`），支持分类、搜索、使用。
- **炼丹/炼器**：阶级/熟练度/成功率/次数，做成小游戏式的"成功率预览 + 掷骰"。

### 3.5 关系（道侣 / NPC / 灵宠）

- **道侣**：亲密/生命/灵力/修为/道心、性格、外观、背景、神通、**心声（内心独白）**——心声单独做"浮字"演出，很有戏剧张力。
- **NPC**：好感（0–100）+ **关系阶段**（陌生→试探期→松动期→信任期→至诚羁绊），做**关系进度可视化**。
- **灵宠**：亲密度、状态、心声。
- **关系图（可选）**：以主角为中心的星图，节点大小=好感，颜色=阵营。

### 3.6 机遇 / 遭遇 / 时间

- **机遇**：任务卡（难度/目标/机缘/引言），最多保留最近 20 条（对应卡内 `takeRight(20)`），已完成归档。
- **动态遭遇**：复刻卡的逻辑——`遭遇冷却 > 0` 禁止偶遇；`= 0` 时按"用户境界 vs 场景（室内/室外）"抽取候选。**抽取改由引擎掷骰 + 检索世界书候选池**，模型只负责"把这次遭遇演得合理"。
- **时间**：引擎维护游戏内时间（现代词表达）、天气、灵气浓度；每次修炼/远行推进。UI 顶部 HUD 常显。
- **危机程度**：无/低/中/高的四档 HUD 指示。

### 3.7 玉简（手机）/ 绝色榜 / Wiki

- **玉简 = 游戏内手机**：卡的 `玉简` 变量 + `phone_data`（角色/背景/聊天记录）证明卡里已有"收发消息"系统。独立版直接做成**手机界面**：好友列表、对话记录（保留最近 100 条）、好感度、发消息触发 LLM 生成回信。
- **绝色榜**：仙子排行榜（排名/头衔/仙姿/群芳谱），做成**图鉴式收集页**，遇到即解锁，鼓励探索。
- **Wiki（术语组件）**：卡外链了 `daoyuan-term-widget`。独立版把 319 条世界书做成**内置图鉴/百科**：正文里出现的专有名词自动可点，弹出条目卡。这也是"可视化展示"的重要一环。

### 3.8 判定与战斗

- **DC 判定**：复刻卡的核心原则「**境界优先级 > DC 数值**」，DC 差 0–2 / 3 / 6 / 9 / 15 / ≥30 六级压制阶梯，本地成表。
- **战斗演出**：不做图形战斗，做"**判定演出**"——出手时 UI 弹出对拼面板：双方 DC、境界差、灵压提示，引擎掷骰给出结果，模型据此演战况。既不破坏文字叙事，又给足游戏感。
- **灵压可视化**：跨越一大境界时，屏幕做"灵压"压迫特效（低阶视角的震颤/模糊）。
- **合理性审查**：卡里"三重人格 + 30 条铁律"是**给模型看的自查提示词**。独立版把它拆成两半：**可确定性的部分（境界/DC/资源品级/称谓辈分）由引擎直接校验并拦截**；**叙事性部分（OOC、情感倒错、剧情套娃）保留为提示词自查**。这样既减负又提准。

### 3.9 存档与结局

- **多存档**：每档含 `GameState`（结构化）+ `ChatLog`（叙事流）+ `WorldState`（已解锁图鉴/人物）。
- **导入/导出**：JSON 存档 + 可选"卡兼容导出"（把当前存档反向导出成能塞回酒馆的变量 + 世界书，作为迁移/兼容后路）。
- **时间线/回看**：按"章节/地点/时间"给叙事流做索引，支持回看与复盘。
- **成就**：首个金丹、首次渡劫、收集 N 名绝色榜、结成道侣……（本地判定，纯锦上添花）。

## 4. AI 叙事内核（调用优化是重点）

### 4.1 LLM 的职责边界

| 交给 LLM | 不交给 LLM（引擎做） |
|---|---|
| 剧情推进、对白、NPC 反应 | 数值加减、clamp、归零后果 |
| 场景描写、氛围、情感 | DC 查表、境界突破判定 |
| 机遇/任务的"内容" | 时间推进、修炼产出 |
| 把"引擎掷出的结果"演得合理 | 抽气运、动态遭遇抽取 |
| 叙事性一致性自查 | 变量路径落地、存档、检索 |

### 4.2 提示词编排（分层 + 预算）

每回合的上下文按**层级**组装，各层有明确 token 预算与优先级：

| 层 | 内容 | 预算占比 | 缓存性 |
|---|---|---|---|
| L0 系统 | 引擎协议、输出格式、铁律摘要 | 小 | **稳定（可前缀缓存）** |
| L1 世界法则 | 核心规则子集（常驻精简版） | 中 | **稳定** |
| L2 检索记忆 | 本回合命中世界书（见 4.5） | 中 | 动态 |
| L3 状态摘要 | `GameState` 的紧凑快照（非全量） | 小 | 动态 |
| L4 近况 | 最近 N 轮叙事（滑窗/摘要） | 中 | 部分稳定 |
| L5 本回合 | 玩家输入 + 引擎掷骰结果 | 小 | 动态 |

**要点**：L0/L1 尽量稳定不变 → **命中前缀缓存（prefix cache）**，直接省钱省延迟；L2 换检索 → 只在需要时带长设定；L3 用"摘要"而非全量 JSON。

### 4.3 变量更新协议（升级版）

**旧（卡）**：模型在正文里额外输出 `<UpdateVariable><JSONPatch>[...]</JSONPatch>`，手写中文路径。

**新（独立版）**：模型用**结构化输出 / tool-calling**返回：
```json
{
  "narrative": "……正文……",
  "effects": [
    {"op":"delta","target":"主角.灵力","value":-12,"reason":"施展御剑术"},
    {"op":"set","target":"世界.当前地点","value":"青石镇·醉仙楼"},
    {"op":"add","target":"人物.灵玥","value":{"好感":5,...}}
  ],
  "scene": {"时间":"初春·黄昏","地点":"青石镇","危机":"低","天气":"细雨"}
}
```
- `target` 用**扁平路径**，引擎解析 → 定位 → clamp → 落地 → 生成 UI 事件。
- 引擎抛异常/路径未知 → 挂起该 effect 并回灌给模型一次修正（可选），或忽略并记录。
- **好处**：模型不必记忆 Schema 树；输出可被 JSON Schema 强约束；正文与状态彻底解耦，`narrative` 不再被 JSON 污染。

### 4.4 双模型 / 多模型策略

| 角色 | 模型档位 | 用途 |
|---|---|---|
| 叙事模型（主） | 强 / 贵 | 生成 `narrative`，负责文笔与演出 |
| 裁决模型（辅，可选） | 快 / 便宜 | 抽取 effects 的语义、压缩"近况"摘要、检索改写 |

可选：`effects` 抽取用**同一次调用的结构化输出**（单模型单次）以省一次往返；只在需要时启用辅模型做"记忆压缩/检索改写"。用户可在设置中分别配置。

### 4.5 调用优化清单（对照卡片痛点）

| # | 优化项 | 卡的做法 | 独立版做法 | 收益 |
|---|---|---|---|---|
| 1 | **世界书检索** | 常驻 + 手动开关 `getwi()` | 本地索引（关键词 BM25 + 可选向量）混合检索，每回合注入 Top-K（如 5–15 条） | 上下文从"全量 20 万字"降到千级 token |
| 2 | **状态注入** | 每回合全量变量 | 结构化摘要（仅"有变化的 + 关键 field"） | 减 token、减噪音 |
| 3 | **变量落地** | 模型手写 JSONPatch | 模型出语义 effect，引擎落地 | 零掉档、可校验 |
| 4 | **UI 渲染** | 模型吐 HTML + 正则 | 原生渲染，模型不输出 UI | 省下 20 万字状态栏 token |
| 5 | **前缀缓存** | 无 | L0/L1 稳定化 | 命中 prompt cache，省钱省延迟 |
| 6 | **规则判定** | 全押模型 | 引擎掷骰/查表 | 更准、更快、更省 |
| 7 | **创角引导** | 18.5 万字单页提示词 | 本地表单，只把"结果"喂模型 | 创角不再吞上下文 |
| 8 | **记忆压缩** | 无 | 每 N 轮把近况滚动压缩成摘要 | 长局不爆上下文 |
| 9 | **流式 + 增量解析** | 依赖酒馆 | 原生 SSE 流式 + narrative/effects 增量解析 | 首字更快、观感更好 |
| 10 | **模型分级** | 单模型 | 叙事/裁决分离 | 成本可控 |

**预期**：同等体验下，单回合**有效上下文**与**输出 token** 均有数量级下降（世界书注入与状态栏渲染是两大头），长局稳定性显著提升。

## 6. 数据与技术架构

### 6.1 分层架构

```
┌─────────────────────────────────────────────────────┐
│ 表现层 Presentation                                  │
│   叙事流 / HUD / 面板 / 图鉴 / 演出 / 设置            │
├─────────────────────────────────────────────────────┤
│ 游戏内核 Engine（纯 TS，无 UI 依赖，可单测）          │
│   StateStore / Rules(境界·DC·突破·修炼) / Dice        │
│   EncounterEngine / FateDrawer / EffectApplier       │
├─────────────────────────────────────────────────────┤
│ 记忆层 Memory                                        │
│   WorldbookIndex(319条) / Retriever(BM25+向量)        │
│   Summarizer(近况压缩)                                │
├─────────────────────────────────────────────────────┤
│ 叙事层 Narrator                                      │
│   PromptComposer(分层) / LLMClient(多模型/流式)       │
│   EffectParser(结构化输出)                            │
├─────────────────────────────────────────────────────┤
│ 数据层 Persistence                                   │
│   存档(SQLite/JSON) / 资产(图片音频) / 设置            │
└─────────────────────────────────────────────────────┘
```

**内核可单测**是硬要求：规则、判定、抽取、效果落地全部是纯函数，与 LLM 和 UI 解耦，方便回归测试与日后移植。

### 6.2 数据模型（变量 → 类型）

把卡的 Zod Schema 直接翻译成 TypeScript 强类型（见 `附录B·状态数据模型.md` 完整版），要点：

- `GameState { 世界, 主角, 道侣, 灵宠, 人物, 机遇, 绝色榜, 玉简 }`；
- 所有 0–100 字段用 `clamp` 类型守卫；
- `机遇` 保留最近 20、`玉简.历史记录` 保留最近 100（沿用卡规则）；
- `储物袋` 数量归零自动剔除；
- **版本化**：`saveVersion` + 迁移函数，保证 Schema 演进不炸老档。

### 6.3 存档格式

```
save-<id>/
├── meta.json        # 版本/时间/摘要/缩略图
├── state.json       # GameState（结构化状态）
├── chat.jsonl       # 叙事流（每行一条 turn，含 effects 与 scene）
└── world.json       # 已解锁图鉴/人物/绝色榜/足迹
```
另支持 `导出为酒馆兼容包`（可选）：反向生成变量 + 世界书，作为迁移后路。

### 6.4 记忆检索

- **索引**：把 319 条世界书切成条目，建 `keys + comment + 摘要` 的倒排索引；
- **检索**：本回合输入 + 近况关键词 → BM25 召回 → 规则重排（constant 规则条目提权、当前地点/势力/在场人物提权）→ Top-K；
- **进阶**：可选向量召回（本地 embedding），提升近义命中；
- **回退**：检索不到就只注入 L1 核心法则，不硬塞。

### 6.5 技术选型与理由

| 层 | 推荐 | 理由 | 备选 |
|---|---|---|---|
| 外壳 | **Tauri 2**（Rust 芯 + WebView） | 体积小、性能好、跨平台、Web 前端天然富视觉 | Electron（更重但更成熟） |
| 前端 | **TypeScript + React + Zustand + Tailwind** | 富视觉/动画生态最强，可直接复用卡内 HTML/CSS 资产 | Vue 3（若用户更熟） |
| 内核 | **纯 TS 包**（Engine / Memory / Narrator 分离） | 可单测、可移植、可被 CLI 复用 | — |
| 存储 | **SQLite**（存档/图鉴） + JSON（配置） | 查询方便、单文件 | 纯 JSON 文件（更简单） |
| 检索 | 自研 BM25（小体量够用） | 无依赖、可控 | sqlite-vec / 本地 embedding |
| LLM | **OpenAI 兼容客户端**（多 provider） | 通吃官方/中转/Ollama | 各家 SDK |

> **为什么不用 Flutter？** 现有 PocketTavern 是 Flutter，能复用工程；但本项目的重心是**富可视化 + 复用卡内 HTML/CSS**，Web 前端（Tauri 壳）在动画/排版/样式复用上优势明显。若更看重与现有 Flutter 工程一体，可改 Flutter + 自绘 UI，代价是视觉与资产复用成本更高。**建议先做 Web 版（Tauri），内核保持纯 TS，日后可移植。**

   - 方案本身（引擎/界面/调用优化）是通用工程能力，可复用；**但《道渊》的文本、设定、素材的再分发权在原作**。
   - 建议：先确认作者与授权状态 → 决定"私人自用"还是"可分发二创"，并把结论写进项目 README。
