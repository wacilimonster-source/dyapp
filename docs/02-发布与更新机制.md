# 发布与更新机制

> 对应需求：**代码上传到 GitHub + APP 支持检查更新**
> 远端：<https://github.com/wacilimonster-source/dyapp>
> 原型实现：`prototype/update.js`（模块）、`prototype/app.js`（设置页 UI）

---

## 1. 版本号：单一真源

版本号是纯语义化三段式 `主.次.修`，**不带前缀**，存在仓库根的 `VERSION` 文件里：

```
VERSION        →  0.2.0
```

四处引用（`ci.yml` 强制前两处一致，`tools/release-local.sh build` 会检查四处都一致）：

| 位置 | 用途 |
|---|---|
| `VERSION` | 发版校验（tag 必须等于 `v` + 它） |
| `prototype/update.js` 的 `VERSION` 常量 | 客户端运行时比较的"当前版本" |
| `app/src-tauri/tauri.conf.json` 的 `version` | 安装包 / APK 的 versionName |
| `app/src-tauri/Cargo.toml` 的 `version` | Rust 侧版本，保持同号段 |

`ci.yml` 会比对前两处；不一致直接 fail。**改版本要同时改这四处**，然后才打 tag。

> 为什么不用 `package.json`：本仓库当前没有 npm 工程（原型是零依赖静态页），引入一个假 package.json 只为存版本号反而误导。

## 2. 发版流程（本地构建，不走 CI）

> **从 0.10.0 起，发版一律在本机完成，CI 不再构建、不再发版。** `.github/workflows/` 里只剩 `ci.yml` 与 `app-ci.yml`（只做检查）。
> 原因：CI 不持有签名材料（keystore 不入库，这是硬约束），它产出的只能是 `-unsigned.apk`；客户端挑附件时会避开未签名包，
> 结果 v0.9.0 的 Release 上没有任何可装的 APK。本地构建后用 debug 证书签名，才能原地覆盖安装、保留存档。

```bash
# 1) 改版本（四处 + Cargo.lock，用 0.10.0 举例）
echo "0.10.0" > VERSION
#    prototype/update.js           的 const VERSION = '0.9.0'  → '0.10.0'
#    app/src-tauri/tauri.conf.json 的 "version"               → "0.10.0"
#    app/src-tauri/Cargo.toml      的 version                  → "0.10.0"
#    app/src-tauri/Cargo.lock      里 name = "dyapp" 下一行的 version 同步改

# 2) 写这一版的更新说明（进仓库留档，Release 正文取它；缺这个文件脚本会中止）
#    release-notes/v0.10.0.md

# 3) 本地构建 + 签名 + 校验（含前端测试、Rust 测试、cargo fmt）
bash tools/release-local.sh build

# 4) 提交、打 tag、推送（推 tag 不会触发任何构建）
git add -A && git commit -m "release: v0.10.0"
git tag v0.10.0
git push origin main v0.10.0

# 5) 建 Release 并上传附件（只传已签名 APK 与原型 zip）
bash tools/release-local.sh publish
```

`tools/release-local.sh` 做的事：

1. **build**：校验四处版本号一致且存在 `release-notes/<tag>.md` → 跑语法检查、前端测试、`cargo fmt --check`、`cargo test`
   → `cargo tauri android build --apk` → `zipalign` → 用 `~/.android/debug.keystore` 签名
   → `apksigner verify`，并核对**证书 SHA-256 指纹**与 `aapt2` 读到的 `versionName`，对不上就中止。
2. **publish**：要求工作区干净、tag 在当前提交上且已推到远端 → 打包 `prototype/` 为 `dist/dyapp-prototype-<tag>.zip`
   → 建或更新 Release（正文取 `release-notes/<tag>.md`，带 `--draft=false`）→ 上传 `dyapp-<ver>-universal.apk` 与 zip（`--clobber`）。

令牌从 Windows 凭据管理器取（`git credential fill`），只在单条 `gh` 命令内使用，不 `export`、不落盘。取法见本地笔记 `tools/_发版凭据.md`（被 `.gitignore` 的 `tools/_*` 覆盖，不入库）。

**重跑是安全的**：Release 已存在时走 `gh release edit` + `gh release upload --clobber`，只更新说明与附件。

### 签名纪律（避免再出签名问题）

| 规则 | 原因 |
|---|---|
| **只用 `~/.android/debug.keystore` 签**，证书 SHA-256 指纹固定为 `e436a586cde571929d012c964d02a1cca45632abcdb662745b734ddfdb274f06` | 证书与已发布版本不同，系统会拒绝覆盖安装，用户只能卸载重装，存档随之丢失 |
| **绝不上传 `-unsigned.apk`** | 装不上；而且客户端挑附件时会避开未签名包，Release 上只有它等于「没有可用更新」 |
| 附件命名固定为 `dyapp-<版本>-universal.apk` | 客户端按「`.apk` 且不含 `unsigned`」挑选 |
| `release-local.sh` 里写死了指纹，对不上就中止 | 防止换了机器或 keystore 后悄悄发出一个不兼容的包 |
| **换自己的 keystore 之前先导出存档、公告用户** | 换证书等于换了一个应用，旧版用户必须卸载重装 |
| 新机器上要先确认 `~/.android/debug.keystore` 就是原来那份 | 在新机器上自动生成的 debug.keystore 指纹不同，签出来的包无法覆盖安装 |

### 本机前置条件

Rust（MSVC 工具链，`~/.cargo/bin` 不在 PATH，脚本里会自动加）、Tauri CLI 2.x、`ANDROID_HOME=G:\Android`、NDK `27.0.12077973`、JDK 17、build-tools 35.0.0、`gh`、`python`（用于打 zip；注意是 `python`，Windows 上的 `python3` 只是商店占位程序）。详见 `docs/03` 第 7.1 节。

### 历史：CI 发版时期踩过的坑（仅留档，CI 发版已停用）

| 坑 | 现象 | 教训 |
|---|---|---|
| **删 tag 会把 Release 变成草稿** | 删掉远端 tag 重推后，公开 API 查不到 Release，而 `gh release view` 又能看到它 | `edit` 一律带 `--draft=false`；发布后用 `gh release view --json isDraft` 自查（脚本已做） |
| **重跑会拿旧说明覆盖新说明** | 说明在打完 tag 之后才改，重跑时按 tag 检出又盖回旧版 | 现在说明取自本地当前工作区，不再有这个问题 |
| **`gen/android/gradlew` 没有可执行位** | 入库时是 `100644`，Linux 上 `permission denied` | 只对 Linux 构建有影响；本机 Windows 不受影响 |
| **`android-actions/setup-android@v3` 失败** | 该 action 直接报 failure | 本地构建不需要它 |
| **CI 产物是未签名的** | v0.9.0 Release 上只有 `-unsigned.apk`，应用内更新找不到可装的包 | 这是改为本地构建的直接原因 |

## 3. 客户端「检查更新」如何工作

实现见 `prototype/update.js`，逻辑极简：

```
GET https://api.github.com/repos/wacilimonster-source/dyapp/releases/latest
  ├─ 200 → 取 tag_name，与本地 VERSION 做语义化比较
  │        ├─ 远端更新 → status = newer  （展示更新说明 + 下载按钮）
  │        └─ 持平或更旧 → status = latest
  ├─ 404 → 尚无 Release      → status = none（当作最新开发版）
  ├─ 403 → GitHub 限流       → status = error
  └─ 其它/超时/断网          → status = error
```

### 触发时机

| 场景 | 行为 |
|---|---|
| 启动时 | 若「启动时自动检查更新」开启（默认开），**静默**检查一次；有新版本才在启动页显示一枚胶囊「发现新版本 v0.2.0 · 查看」 |
| 设置页 | 「检查更新」按钮，手动触发；结果就地显示 |
| 关闭自动检查 | 设置页开关，写入 `localStorage['dy.update.auto'] = '0'`，此后启动不再联网 |

### 硬约束（都已实现）

1. **离线优先**：任何失败都只是提示「检查失败：…（不影响离线游玩）」，绝不阻塞、不弹窗打断。
2. **不打扰**：自动检查的新版本提示是可点的胶囊，不是强制弹窗。
3. **不传数据**：只发一个 GET，不带任何本地存档、设备标识、统计字段。
4. **超时**：8s `AbortController` 超时，避免弱网下挂住。
5. **并发去重**：`inflight` 变量保证同一时刻只有一次请求。
6. **只读版本号**：远端返回的内容只用于**显示文本**，绝不 `eval` 或执行远端代码。

### 已知限制

- 未认证的 GitHub API 限流是 **60 次/小时/IP**。单机游戏一次启动一次请求，远够用；但如果玩家反复点「检查更新」，会撞 403——UI 已给出明确提示。真机若不放心，可后续换成**自托管静态 `latest.json`**（无 CORS、无严格限流，代价是要自己托管）。
- `api.github.com` 支持 CORS，浏览器/WebView 直连可用；若日后换成自托管，记得带 `Access-Control-Allow-Origin`。

## 4. 安卓端落地差异

原型里点「下载」是打开浏览器页面；真机要变成**下载 APK 并触发安装**：

| 环节 | 做法 |
|---|---|
| 取下载地址 | Release asset 里的 `*.apk`（`update.js` 已经把它的 `browser_download_url` 解析到 `state.apk`） |
| 下载 | 壳侧（Tauri 命令 / Capacitor 插件）下载到应用私有目录并校验 |
| 安装 | 走系统安装器：`Intent.ACTION_VIEW` + `application/vnd.android.package-archive`，配 `FileProvider` 共享 URI |
| 权限 | Android 8.0+ 需 `REQUEST_INSTALL_PACKAGES`；运行时引导用户到「安装未知应用」设置页 |
| 校验 | 取 GitHub API 返回的资产 `digest`（`sha256:…`），下载时边写盘边算 SHA-256，下完比对，不一致就丢弃并换下一个来源 |
| 保底 | 安装失败/权限被拒时，回退为"打开 Release 页面手动下载" |

### 国内网络下的下载来源

`github.com` 的 Release 下载在国内常常连不上（TCP 悬着不拒绝，不会快速报错），`update_download` 因此按下面顺序逐个尝试，单个来源失败就换下一个，全部失败才报错并列出每个来源的原因：

1. `ghfast.top` 转发
2. `gh-proxy.com` 转发
3. `github.com` 直连

约束：

- 镜像是第三方，能改文件内容，所以**只有请求带了 SHA-256 才启用镜像**；没有哈希只走直连。下完比对哈希，对不上就丢弃。
- 镜像列表写死在 `update.rs` 的 `MIRRORS`，不接受前端传入，避免页面被注入后把"下载并执行"指向任意域名。
- 超时：建立连接 8 秒（`CONNECT_TIMEOUT`），连上后两次收到数据之间最长 20 秒（`STALL_TIMEOUT`）。两者都不限制总时长，慢网下大文件仍能下完。
- 检查更新（`update.js`）同样先直连 `api.github.com`，失败（超时 / 5xx / 429）再回退到 `gh-proxy.com` 转发。`ghfast.top` 不转发 API，所以不在这条链上。
- 镜像会失效或限流（2026-11 实测 `ghproxy.net` 很慢，`mirror.ghproxy.com`、`github.moeyy.xyz`、`gh.llkk.cc` 不通，`gh.ddlc.top` 返回 429），列表需要定期复测。

### 两条路线对比

| 方案 | 现状实现 | 优点 | 代价 |
|---|---|---|---|
| **GitHub Releases API**（当前） | 已实现，纯前端、跨壳通用 | 零服务端、跨 Tauri/Capacitor 都能用 | GitHub 限流；无签名校验 |
| **Tauri 2 官方 updater 插件** | 待接入 | 内置**签名校验**、增量更新、体验最好 | 需生成并保管签名密钥；需一个静态 `latest.json`（HTTPS） |

**建议**：原型阶段用现在的 Releases 方案把流程跑通；等安卓壳工程（M0 之后）落地，再切到 **Tauri updater + 签名**，把 GitHub Releases 只当分发渠道。迁移成本主要在壳侧，`update.js` 的版本比较与 UI 逻辑可原样保留。

## 5. 安全与隐私边界

- 全程 **HTTPS**；连 `api.github.com`、GitHub 下载域名，以及 `MIRRORS` 里写死的国内转发镜像（见 §4，镜像下载强制 SHA-256 校验）。
- 不引入任何统计 / 上报 / 崩溃采集 SDK。
- 更新说明文本在 UI 里**按纯文本转义渲染**（`esc()` + `white-space: pre-wrap`），不解析 HTML。
- 存档、设置、世界书全在本地；更新检查是**唯一**的主动出网行为，且可关闭。
- 首次运行建议（Android）：在设置页显著位置说明"本作唯一联网行为是检查更新与调用你自己配置的 LLM"。
