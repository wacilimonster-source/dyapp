# 发布与更新机制

> 对应需求：**代码上传到 GitHub + APP 支持检查更新**
> 远端：<https://github.com/wacilimonster-source/dyapp>
> 原型实现：`prototype/update.js`（模块）、`prototype/app.js`（设置页 UI）

---

## 1. 版本号：单一真源

版本号是纯语义化三段式 `主.次.修`，**不带前缀**，存在仓库根的 `VERSION` 文件里：

```
VERSION        →  0.1.0
```

两处引用，CI 强制它们一致：

| 位置 | 用途 |
|---|---|
| `VERSION` | 发版校验（tag 必须等于 `v` + 它） |
| `prototype/update.js` 的 `VERSION` 常量 | 客户端运行时比较的"当前版本" |

`ci.yml` 会比对两者；不一致直接 fail。**改版本必须同时改这两处**，然后才打 tag。

> 为什么不用 `package.json`：本仓库当前没有 npm 工程（原型是零依赖静态页），引入一个假 package.json 只为存版本号反而误导。

---

## 2. 发版流程

```bash
# 1) 改版本（两处）
echo "0.2.0" > VERSION
#    再把 prototype/update.js 里的 const VERSION = '0.1.0' 改成 '0.2.0'

# 2) 提交
git add -A && git commit -m "release: v0.2.0"

# 3) 打 tag 并推送
git tag v0.2.0
git push origin main --tags
```

CI（`.github/workflows/release.yml`）随后自动：

1. 校验 `tag` == `VERSION`（不等则中止）；
2. 打包 `prototype/` 为 `dyapp-prototype-v0.2.0.zip`；
3. 用 `gh release create --generate-notes` 建 Release，Release 正文即更新说明。

安卓壳工程接入后，在同一个 workflow 里加 Gradle / Tauri 构建步骤，把 **APK 也作为 asset 上传**，客户端就能直接下载安装（第 4 节）。

## 3. 客户端「检查更新」如何工作

实现见 `prototype/update.js`，逻辑极简：

```
GET https://api.github.com/repos/wacilimonster-source/dyapp/releases/latest
  ├─ 200 → 取 tag_name，与本地 VERSION 做语义化比较
  │        ├─ 远端更新 → status = newer  （展示更新说明 + 下载按钮）
  │        └─ 持平或更旧 → status = latest
  ├─ 404 → 尚无 Release      → status = none（当作最新开发版）
  ├─ 403 → GitHub 限流       → status = error
  └─ 其它/超时/断网          → status = error
```

### 触发时机

| 场景 | 行为 |
|---|---|
| 启动时 | 若「启动时自动检查更新」开启（默认开），**静默**检查一次；有新版本才在启动页显示一枚胶囊「发现新版本 v0.2.0 · 查看」 |
| 设置页 | 「检查更新」按钮，手动触发；结果就地显示 |
| 关闭自动检查 | 设置页开关，写入 `localStorage['dy.update.auto'] = '0'`，此后启动不再联网 |

### 硬约束（都已实现）

1. **离线优先**：任何失败都只是提示「检查失败：…（不影响离线游玩）」，绝不阻塞、不弹窗打断。
2. **不打扰**：自动检查的新版本提示是可点的胶囊，不是强制弹窗。
3. **不传数据**：只发一个 GET，不带任何本地存档、设备标识、统计字段。
4. **超时**：8s `AbortController` 超时，避免弱网下挂住。
5. **并发去重**：`inflight` 变量保证同一时刻只有一次请求。
6. **只读版本号**：远端返回的内容只用于**显示文本**，绝不 `eval` 或执行远端代码。

### 已知限制

- 未认证的 GitHub API 限流是 **60 次/小时/IP**。单机游戏一次启动一次请求，远够用；但如果玩家反复点「检查更新」，会撞 403——UI 已给出明确提示。真机若不放心，可后续换成**自托管静态 `latest.json`**（无 CORS、无严格限流，代价是要自己托管）。
- `api.github.com` 支持 CORS，浏览器/WebView 直连可用；若日后换成自托管，记得带 `Access-Control-Allow-Origin`。

## 4. 安卓端落地差异

原型里点「下载」是打开浏览器页面；真机要变成**下载 APK 并触发安装**：

| 环节 | 做法 |
|---|---|
| 取下载地址 | Release asset 里的 `*.apk`（`update.js` 已经把它的 `browser_download_url` 解析到 `state.apk`） |
| 下载 | 壳侧（Tauri 命令 / Capacitor 插件）下载到应用私有目录并校验 |
| 安装 | 走系统安装器：`Intent.ACTION_VIEW` + `application/vnd.android.package-archive`，配 `FileProvider` 共享 URI |
| 权限 | Android 8.0+ 需 `REQUEST_INSTALL_PACKAGES`；运行时引导用户到「安装未知应用」设置页 |
| 校验 | 建议发布 APK 时附 SHA-256，客户端下载后比对再安装 |
| 保底 | 安装失败/权限被拒时，回退为"打开 Release 页面手动下载" |

### 两条路线对比

| 方案 | 现状实现 | 优点 | 代价 |
|---|---|---|---|
| **GitHub Releases API**（当前） | 已实现，纯前端、跨壳通用 | 零服务端、跨 Tauri/Capacitor 都能用 | GitHub 限流；无签名校验 |
| **Tauri 2 官方 updater 插件** | 待接入 | 内置**签名校验**、增量更新、体验最好 | 需生成并保管签名密钥；需一个静态 `latest.json`（HTTPS） |

**建议**：原型阶段用现在的 Releases 方案把流程跑通；等安卓壳工程（M0 之后）落地，再切到 **Tauri updater + 签名**，把 GitHub Releases 只当分发渠道。迁移成本主要在壳侧，`update.js` 的版本比较与 UI 逻辑可原样保留。

## 5. 安全与隐私边界

- 全程 **HTTPS**；只连 `api.github.com` 与 GitHub 下载域名。
- 不引入任何统计 / 上报 / 崩溃采集 SDK。
- 更新说明文本在 UI 里**按纯文本转义渲染**（`esc()` + `white-space: pre-wrap`），不解析 HTML。
- 存档、设置、世界书全在本地；更新检查是**唯一**的主动出网行为，且可关闭。
- 首次运行建议（Android）：在设置页显著位置说明"本作唯一联网行为是检查更新与调用你自己配置的 LLM"。
