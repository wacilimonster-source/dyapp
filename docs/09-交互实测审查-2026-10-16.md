# 交互实测审查（2026-10-16）

> 触发：v0.6.0 之后的一次"体验是否还合理"的复查。方法与上一轮（`docs/07`）不同——
> 这次不是看设计稿，而是**用本机 Edge（Chromium）在真视口下把原型跑起来**：手机 390×844、平板横屏 1024×768、平板竖屏 800×1280，
> 逐屏点进创角 6 步、主循环、判定演出、抽屉 15 个面板，**量取每个区块的实际像素**。
> 上一轮已裁决并落地的项（两级折叠、建议吸附、抽屉分组、平板竖屏默认收右栏、正文限宽）**不重复报告**。

---

## 0. 一句话结论

交互骨架是合理的，**手机端尤其**（操作区 27% 屏高、正文占 62%，与上一轮的目标一致）。
但有三处真问题：**平板横屏右栏收不起来**（按钮逻辑反了）、**行动栏被新加的「斗法」挤变形**（布局没跟着改）、
**平板左栏 15 个入口装不下 4 个**（模型/同步/设置/主菜单要盲滑才找得到）。
另有两条是"新功能带来的密度"问题：立绘让绝色榜每张卡 373px 高、气运步一屏 20 张候选卡。二者都不算 bug，但会让人多滑很多下。

**这三处已修、两条密度问题一项改三列一项维持现状，改前/改后的实测对照见第 6 节。**

---

## 1. 三处真问题

### 1.1 平板横屏：右栏收不起来（按钮语义反了）

| 项 | 实测 |
|---|---|
| 操作 | 点右栏标题右侧的 `›`（title 写的是"收起右栏"） |
| 结果 | 右栏 **372px → 372px**，`class` 仍是 `sidebar`（没有 `mini`），无任何变化 |
| 代码 | `prototype/app.js:208` `toggleSide(force)`：`sideCollapsed = !force`；而按钮传的是 `toggleSide(true)` → 恒等于"展开" |
| 影响面 | 平板横屏（1024×768）正文只有 566px；想把右栏收掉腾地方的人，点箭头没反应；平板竖屏因为默认就收着，问题被掩盖了 |

`applyCollapse()` 把 `.sidebar.mini` 设成 `display:none`（不是收成细条），所以收起后要靠点左栏图标唤回——这条路径是通的（`openPanel()` 里会自动展开）。

### 1.2 行动栏：「交流」被挤成 52px 宽，「更多」掉到第二行独占一行

| 元素 | 实测（手机 390×844 与平板一致） |
|---|---|
| 探索 / 修炼 / 突破 / 斗法 | 各 **117×58** |
| **交流** | **52×58**（被挤进本该给「更多」的那一格） |
| 更多 | 单独占第二行，右侧 4/5 空着；手机端白占 **~73px ≈ 屏高 8.6%** |
| 代码 | `styles.css:210` `.row-main { grid-template-columns: repeat(4, 1fr) 52px }` —— 模板写的是 **4 主行动 + 更多**，但 `MAIN_ACTS` 现在是 **5 个**（v0.6.0 加了「斗法」），6 个子元素撞进 5 个格子 |

即"加斗法时布局没跟着改"。手机和平板都受影响，且是**每屏都在的**浪费。

### 1.3 平板 1024×768：左栏 15 个入口，有 4 个要盲滑才看得见

| 项 | 实测 |
|---|---|
| 左栏内容高度 | **1013px**（15 个 56px 图标 + logo） |
| 可视高度 | **768px** |
| 首屏看不到的 | **🔌模型、☁同步、⚙设置、⎋主菜单** |
| 滚动提示 | `overflow-y: auto` 但没有滚动条/渐隐提示，视觉上"到底了" |

要命的是被顶下去的恰好是三个**配置类入口**（模型/同步/设置）——第一次装机的人最先要找的就是它们。
平板竖屏（1280 高）不存在这个问题；只有 768 高的横屏（也是多数安卓平板的横屏高度）会撞上。

## 2. 两处"密度"问题（不是 bug，是多滑几下）

### 2.1 绝色榜立绘让每张卡 373px 高

| 项 | 实测 |
|---|---|
| 单卡高度 | **373px**（立绘 2:3 占大头） |
| 手机抽屉可视 | 649px → **5 张卡 = 1.9 屏**；满 20 位约 7–8 屏 |
| 出图 | 3/3、人物 3/3、道侣 1/1 均为 1024×1536 原图，未解锁位显示「？」——**热链方案本身是通的** |
| 流量 | 这次**没能测到**：跨域图片不给 `transferSize`（读数为 0）。沿用发布前的实测口径：一张约 2.5MB，20 位满页 ≈ 50MB |

立绘确实好看（这是这次改动的目的），代价是收集页从"一屏看完"变成"翻半天"。

### 2.2 创角气运步：一屏 20 张候选卡

凡道 10 + 合欢 10，每张卡都带**逐字原文描述**（这是刻意保真的结果），`#cr-body` 实测 647px（占屏 77%），
要滑若干屏才能看完候选。原文不该删（上一版就是删代价删出问题的），但"默认全展开"值得再想。

## 3. 已经合理的部分（实测，供对照）

| 项 | 实测值 |
|---|---|
| 手机操作区总高 | **228px / 844 = 27%**（建议 43 + 行动 120 + 输入 48 + 内边距） |
| 手机正文可视 | **524px = 62%** —— 上一轮"两级折叠 + 建议吸附"的目标达成 |
| 抽屉 tab 条 | 15 个 tab **一屏全可见**（可视 91px，`flex-wrap` 生效，不需要横滑） |
| 创角 | 底部主按钮 50–73px；确认页信息完整；步骤条随难度档变 5/6 步 |
| 判定演出 | 覆盖层 342×357，层级清楚（对方 DC → 成/败 → 档位 → 掷骰依据 → 「承认结果」）；「承认结果」按钮 50px+ |
| 平板竖屏 800×1280 | 默认收右栏 → 中栏 714px（正是上一轮的设计意图） |
| 平板正文行宽 | 中栏 566px、气泡 401px ≈ 25 字/行（可接受区间的偏窄端） |
| 触控目标 | 行动区主按钮 58px、创角按钮 50–73px、判定按钮 50px+ 都达标 |

**触控目标偏小的只有三处**：`#hud-menu`（☰）38×38、行动建议胶囊高 35px、抽屉 tab 高 34px。
都在通用标准（40–44px）之下，单手拇指操作会偶尔点偏，但不是致命项。

## 4. 这一轮无法验证的（如实写明）

1. **软键盘弹出后输入框是否被遮**：代码里有 `visualViewport` 逻辑，但无头浏览器没有虚拟键盘，测不了。
2. **安卓物理/手势返回键**：`docs/04` 第 5.1 节定义为"未实现"，本轮仍无法在真机上验。
3. **立绘真实流量**：跨域拿不到传输字节数（`transferSize=0`），只能引用发布前单张实测 2.5MB。
4. **点按手感（动效、连点、误触）**：`Page.captureScreenshot` 拿得到静态帧，拿不到 60fps 手感；这部分只能真机判断。

## 6. 本轮修复（2026-10-16，按"按你的推荐来"执行）

第 1–4 项按推荐落实；第 5、6 项**经实测后改为维持现状**，理由写在表下。
所有数字都是同一套 CDP 脚本在真视口下重新量出来的（改前 → 改后）。

| # | 项 | 选择 | 改前 → 改后（实测） |
|---|---|---|---|
| 1 | 平板横屏右栏收不起来 | A 修成真切换 | 点箭头 `372px/不变` → **`0/none`（收起）**；中栏 566 → **760px**；点左栏图标可唤回 |
| 2 | 行动栏被「交流」挤变形 | B 五个主行动等分一行 | 交流 `52×58` + 更多独占第二行 → **六格一行各 57×58**；`#actions` 228 → **175px**，正文可视 524 → **572px** |
| 3 | 平板左栏装不下 | A 配置项钉底 + 矮屏压缩到 48px | 「模型/同步/设置/主菜单」首屏不可见 → **底部钉的 5 项（存档/模型/同步/设置/主菜单）常驻可见，中段 8/11 可见，只剩「地图/图鉴/成就」需要滚动**（三者都是"看"的入口） |
| 4 | 触控目标偏小 | A 统一到 `--tap`(44px) | ☰ 38 → **44**；建议胶囊 35 → **44**；抽屉 tab 34 → **44**；设置页字号按钮 **15×24 → 44×44**；全局体检 `<40px` 命中数：3 → **0** |
| 5 | 绝色榜立绘密度 | 见下 | 单卡 373 → **316**；每行 2 → **3**；满 20 位 **5.9 屏 → 3.3 屏**；出图 3/3 不变 |
| 6 | 气运候选一屏 20 张 | 见下 | 实测**只要 2.4 屏**（内容 1564 / 可视 647） |

**第 5 项的取舍**：没有改成"点开才加载图"——图是他点名要的功能，默认无图会让图鉴页看起来是空的。
改为**手机端三列**（`.grid-cards` 在 phone 下 `minmax(108px,1fr)`）：立绘正好是 2:3 不裁切，
卡片变矮、一屏多看一张，密度问题解决一半，视觉收益全留。

**第 6 项的取舍**：量出来只有 2.4 屏（候选 10 张、描述中位 63 字），不是原先估的"长滑"。
描述原文是"选择"的实质依据（上一版删代价删出过问题），折叠成摘要反而要逐条点开，**维持现状**。

### 修复过程中连带发现并修掉的

- **`.sb-tabs` 的高度上限与 tab 高度耦合**：tab 从 34 → 44px 后，原 `max-height:132px` 会把展开「更多」的
  第 4 行裁掉，而被裁的恰好是「存档 / 模型 / 同步 / 设置」。上限改 212px（4 行 × 44 + 3 × 6 + 16 = 210），
  实测 `条高 211 / 内容 210 / 被裁：无`。
- **媒体查询被同特异性规则盖掉**：矮屏压缩规则原先写在 `.rbtn` 基础规则之前，同特异性被后者覆盖，
  量出来没生效（中段内容仍 656px）。移到之后才生效（612px）。
- **设置页「小/中/大」字号按钮是裸按钮**：15×24px，手机上点不中且没有选中态，已补最小尺寸与高亮。
- **气运库/模型点选弹层里的「选」按钮只有 52×30**、弹层右上角关闭键 34×34，一并抬到 44px
  （200 行列表本身可滚，行高不变 —— 行高由气运原文文字撑着，不是按钮撑的）。
- **新档主角面板三个字段空白**：`容貌 / 身形 / 衣着` 由模型在首回合写，创角阶段为空，界面上是三行空标签
  （像坏了）。改为空值时显示「未定」。
- **踩到一个测量陷阱，记下来**：判断"元素是否可见"只比 `bottom <= 容器 bottom` 是错的——
  祖先容器 `overflow:auto` 会把子元素裁掉，但子元素的 rect 仍然算在祖先范围内，于是量出"16/16 全部可见"
  这种假绿。正确口径是"元素 rect 必须落在滚动容器的可视框内"（`top >= box.top && bottom <= box.bottom`）。
  改用这条之后，左栏的真实结论才是"中段 8/11 可见"。
